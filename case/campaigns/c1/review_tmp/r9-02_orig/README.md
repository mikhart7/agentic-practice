# r9-02: ансамбль энкодеров + лексика с весом, зависящим от уверенности лексики (gate по пику триграмм); выбор повторной групповой CV

Родители: r8-01 (ансамбль bge-base/e5-small-v2/all-MiniLM-L6-v2 + центрирование + лексика с фиксированным весом 0.1, train_curve 0.800), r9-01 (анализ CV: граф навыков и GBDT не дают прироста, зато показывают, где лексика вредит). Claim: `board/claims/R9.md`.

## Гипотеза
В CV на fit-выборке (556 запросов) лексика с фиксированным весом даёт +0.5 п.п. к ансамблю, но на indirect теряет (ensemble 0.699 -> 0.652): в 13 запросах indirect лексика ломает верный ответ ансамбля, в 3 чинит. Ломает там, где у запроса нет похожих на слова каталога слов (максимум косинуса триграмм запроса по каталогу `tpk` низкий: в среднем 0.20 у indirect против 0.33-0.44 в других стилях; AUC «indirect по низкому tpk» 0.87), а совпадения лексики — случайные корни/подстроки («stats» -> gitlab, «ads» -> rss). Гипотеза: вес лексики должен зависеть от абсолютной уверенности лексики: низкий при малом `tpk`, выше (до 0.5 вместо 0.1) при большом. Тогда сохраняется выигрыш на question/verbose/cmd и убирается потеря на indirect.

## Механизм
- Dense-стадия — как r8-01 (`build.py`: четыре энкодера через sentence-transformers как эталон, проверка numpy-энкодера для solve, центрирование, веса ансамбля {0,1,2} по метрике на 556 записях fit, простота при разнице <= 0.002).
- Слияние `gate` (`hyb.py`): `score = z(ансамбль) + w(q) * z(лексика)`, `w(q) = wmax * sigmoid((tpk - c) / s)`, где `tpk` — максимум по каталогу косинуса символьных триграмм запроса (лексика `lex.py` r1-03: BM25 + триграммы). Параметры (wmax, c, s) — сетка 196 точек, подбираются внутри каждого фолда.
- Выбор метода среди `wz`, `wz2`, `gate` (и `ens` как нулевой): повторная групповая 5-fold CV по семействам на 3 разбиениях (seeds 0, 1, 2), метрика усредняется по запросам; лексика включается при выигрыше >= 0.004 над `ens`, среди методов с лексикой выбирается самый простой в пределах 0.003 от лучшего. `report.json`: CV по методам и стилям, по повторам, парные сравнения, `tri_peak_by_style`, итоговая выбранная конфигурация (`fusion_final`, `choice`). Итоговые параметры записаны в `/assets/prepared/fusion.json`.
- `solve.py`: кодирует запрос выбранными моделями (numpy), центрирование, z, лексика; метод и параметры из `fusion.json`; топ-3. `fit.jsonl` не читает.

## Происхождение train-сведений (ADR-0004: обучение на train в build)
- `fit.jsonl`: 556 записей `case/dataset/train.jsonl` (id, input, primary/relevant, family, style) без всех 50 семейств `case/dataset/train_curve.jsonl` (тот же файл, что у r5-02/r6-01/r8-01/r9-01). Замер на train_curve — на невиденных навыках и запросах.
- Назначение: только обучение общего механизма в build: средние запросов (центрирование), веса ансамбля, три скаляра gate. Таблиц «запрос -> ответ» и правил под запросы нет; solve записи train не читает.

## Риски
Выбор метода и gate-параметров по 556 запросам: оптимистичная CV (шум ~1.7 п.п. по одному разбиению; повторные разбиения усредняют, но выборка одна). На train_curve ожидается мало отличий от r8-01: по ответам r6-01/r8-01 на curve запросы с низким `tpk` у обоих неверны (лексика там не вредит на этих 50 indirect). Время solve = r8-01.
