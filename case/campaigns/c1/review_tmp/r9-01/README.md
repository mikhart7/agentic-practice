# r9-01: граф навыков (PRF, сглаживание, хабы) и GBDT-ранжировщик поверх ансамбля r8-01; метод выбирает build по групповой CV

Родители: r8-01 (ансамбль bge-base/e5-small-v2/all-MiniLM-L6-v2 + центрирование + лексика, train_curve 0.800), r6-01, r4-01. Claim: `board/claims/R9.md`.

## Гипотеза
Узкое место — indirect (acc@1 ~0.6) и «близнецы» в кластере каталога: у r8-01 на curve 47 промахов acc@1, у 27 золотой в топ-3, но не первый, у 20 (15 из них indirect) его нет в топ-3. Линейные слияния сигналов (r4, r8) выжаты. Новые рычаги: (А) кластерная информация каталога (граф близких навыков по эмбеддингам описаний — производная от исходных описаний), (Б) нелинейный ранжировщик над навык-независимыми признаками пары.

## Механизм
- Dense-стадия и базовая оценка — как r8-01 (`build.py` кодирует каталог и 556 запросов четырьмя энкодерами, проверяет numpy-энкодер, центрирование, ансамбль с весами {0,1,2} по метрике на 556 запросах; лексика r1-03 `lex.py`; базовая оценка `base = z(ансамбль) + 0.1*z(лексика)`).
- (А) `rank.py`: граф навыков G = взвешенное среднее косинусов центрированных эмбеддингов описаний (веса ансамбля), 10 ближайших соседей. Методы: `prf` — псевдо-релевантная обратная связь (Rocchio: q' = q + a*mean(топ-k навыков по базовой оценке), в пространстве оценок = базовая оценка + a * средняя близость навыка к топ-k); `sm` — сглаживание (оценка + b * средняя оценка k соседей навыка); `prfsm` — оба; `csls` — вычитание хаб-статистики навыка (среднее 10 лучших z-оценок навыка по запросам train, без меток). Параметры (k, a, b, g) выбираются сеткой внутри каждого фолда CV.
- (Б) GBDT: кандидаты — топ-30 по базовой оценке; ~38 навык-независимых признаков пары (z и log-ранги каждой модели, лексика BM25/триграммы, разрывы с лидером и вторым, оценки и разрывы k соседей, близость навыка к лидеру и вице-лидеру, число соседей навыка в топ-3, доля навыка в массе кластера, PRF-признаки, плотность окружения, длина запроса, поля запроса: запас лидера, пик лексики, число навыков с общими словами). ID навыка и любые категориальные признаки навыка не используются. LightGBM `lambdarank` или `binary`, сетка 8 конфигураций (листья 4/8, 80/200 деревьев), параметры по CV. Деревья после обучения сериализуются в `gbdt.json`; solve считает их numpy (`rank.predict_trees`), `lightgbm` в solve не импортируется. Build сверяет numpy-оценку с LightGBM (max diff < 1e-6), иначе GBDT исключается.
- Выбор: групповая 5-fold CV по семействам (одно семейство = один навык, отложенное семейство = ещё не виденный навык), метрика кейса по полному ранжированию 189 навыков. Среди новых методов (`csls`, `prf`, `sm`, `prfsm`, `gbdt`) берётся лучший по CV (при разнице <= 0.002 — более простой). В `report.json`: CV по всем методам, включая `ens` и `wz` (r8-01), по стилям, парные сравнения с `wz`, выбранные параметры по фолдам, важность признаков GBDT, число кандидатов, ошибки. Итоговая выбранная конфигурация — `fusion_final` в `report.json` и `fusion.json` в `/assets/prepared`.
- `diag.npz` в выходе build: z-оценки моделей и лексика на 556 запросах fit, метки, фолды, граф — диагностика, считается в runner, solve её не читает, в пакет не переносится.
- `solve.py`: кодирует запрос выбранными моделями (numpy), центрирование, z, лексика, затем метод из `fusion.json` теми же функциями `rank.py`/`hyb.py`; топ-3. `fit.jsonl` не читает.

## Происхождение train-сведений (ADR-0004: обучение на train в build)
- `fit.jsonl`: 556 записей `case/dataset/train.jsonl` (id, input, primary/relevant, family, style) без всех 50 семейств `case/dataset/train_curve.jsonl` (тот же файл, что у r5-02/r6-01/r8-01). Замер на train_curve идёт на невиденных навыках и запросах.
- Назначение: только обучение общего механизма в build: средние запросов (центрирование), веса ансамбля, параметры графовых методов (1-4 скаляра), деревья GBDT над навык-независимыми признаками. Таблиц «запрос -> ответ» и правил под запросы нет; solve записи train не читает.
- Статистика хабов навыков берётся по запросам fit без меток; граф — только из описаний каталога.

## Риски
Выбор из ~12 методов и 8 конфигураций GBDT по 556 запросам: оптимистичная CV (шум ~1.7 п.п.). GBDT на ~550 запросах может переобучиться; защита — малые деревья, bagging, L2 и CV по семействам. Время solve = r8-01 + граф/признаки (десятки мс).
