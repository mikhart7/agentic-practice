# r6-01: ансамбль энкодеров (bge-base, e5-small-v2, all-MiniLM-L6-v2, bge-small) с центрированием, слияние выбирается в build групповой CV

Родитель: r5-02 (центрирование bge-base; CV 0.8004, train_curve 0.77275). Claim: `board/claims/R6.md`.

## Гипотеза
Прежние dense-кандидаты используют один backbone. Разные энкодеры ошибаются по-разному (разные обучающие данные и токенизация), поэтому слияние их оценок после центрирования каждого пространства даёт acc@1 выше сильнейшей одиночной модели.

## Механизм
- `build.py` (runner): для каждой модели из `params.json` (порядок: bge-base, e5-small-v2, all-MiniLM-L6-v2, bge-small; новая модель не начинается после 330 с) кодирует каталог и 556 запросов `fit.jsonl` через sentence-transformers; проверяет numpy-энкодер (`enc.py`, он используется в solve) против эталона (косинус > 0.999 на пробах и выборке документов). Префиксы: bge - запрос без префикса + с инструкцией BGE (ансамбль как у r2-04), e5 - `query: ` / `passage: `, MiniLM - без префиксов; пулинг по конфигам моделей (bge: CLS, e5 и MiniLM: mean), нормализация L2.
- Центрирование каждой модели: из эмбеддинга запроса вычитается среднее эмбеддингов запросов train, из эмбеддинга навыка - среднее по каталогу, затем L2-нормировка (как r5-02).
- Слияние (`fusion.py`, единая реализация для build и solve): `z` - оценки модели стандартизуются по навыкам внутри запроса, взвешенная сумма; `rrf` - сумма w/(k+ранг). Перебор: z с весами {0,1,2}^4 (>= 2 моделей), RRF k=10/60 с весами {0,1}^4. Выбор: 5-fold CV по семействам (оценки каждого запроса получены с mu_q обучающей части фолда), метрика кейса; при разнице <= 0.002 от лучшего - конфигурация с меньшим числом моделей. Одиночные модели и ансамбли, оракул, согласие top-1, CV по стилям пишутся в `report.json` (одиночные модели - справка, в выбор не входят: результат r6-01 всегда ансамбль).
- `solve.py`: загружает только выбранные модели (вес > 0), кодирует запрос, центрирует, косинус с `emb_<модель>.npy`, слияние, топ-3. Каталог и fit.jsonl не читает.

## Происхождение train-сведений (ADR-0004: «обучение на train: калибровка»)
- `fit.jsonl`: 556 записей `case/dataset/train.jsonl` (id, input, primary/relevant, family, style) без всех 50 семейств `case/dataset/train_curve.jsonl`; поэтому замер на train_curve сопоставим и не использует ни запросы, ни навыки curve. Тот же файл, что у r5-02.
- Назначение: средний вектор запросов каждой модели (768/384 чисел) и выбор режима/весов слияния групповой CV. Таблиц «запрос -> ответ» и правил под запросы нет; solve записи train не читает.
- Для итогового кандидата fit.jsonl можно расширить записями curve (тогда curve перестанет быть независимым замером).

## Риски
Выбор слияния из ~80 конфигураций по 556 запросам: переобучение выбора на CV (шум CV ~1.7 п.п.), смягчено правилом простоты и тем, что веса дискретные (0/1/2). Время solve: несколько моделей на пример (загрузка весов ~0.9 ГБ в сумме).
