# Claim R7 (ветка r7-combine, направление 7: комбинация лучших механизмов)

Дата: 2026-11-05. Квота: 3 места (r7-01 ... r7-03). Родители: r4-01 (гибрид, 0.7825), r5-02 (центрирование, 0.77275), r3-02 (кросс-энкодер).
Не пересекаюсь с R6 (ансамбль разных dense-энкодеров без лексики): моя линия — один dense (bge-base) + лексика + центрирование + кросс-энкодер как признак.

## Анализ ошибок r4-01 на train_curve (чистый Python по `runs/r4-01-curve.json`)
49 промахов acc@1 из 200: золотой навык на 2-м месте 12, на 3-м 10, вне топ-3 27 (из них indirect 18). Промахи с золотым в топ-3 (22): близкие навыки одного кластера (slack-explorer vs mcp-server-slack, kubeview vs другой devops, calendar: holiday-calendar vs google-cal-mcp), «ловушечные слова» (image search -> gemini-image-studio), где нужен совместный разбор запроса и описания. Это зона для кросс-энкодера; indirect (18 промахов вне топ-3) он не исправит, если кандидаты берутся из топ-N гибрида.

## Гипотезы и проверки
1. Центрирование dense внутри гибрида аддитивно (r5-02: +2.4 п.п. CV над dense). Проверка: CV в build (556 запросов, 139 семейств): лучший метод cen против raw; опровержение: разница < 0.3 п.п.
2. Кросс-энкодер MiniLM как признак на кандидатах (топ-8 dense + топ-8 лексики) поднимает acc@1 за счёт 22 промахов «золотой в топ-3»; ожидаемый CV-прирост 1-3 п.п., на curve +0.01..0.03 при цене порядка секунды (numpy-кросс-энкодер). Опровержение: прирост CV < 1 п.п. (правило выбора build не включит CE); либо CV-прирост не переносится на curve.
Обе проверки собраны в один пакет r7-01: build сравнивает 4 варианта на одних фолдах и применяет заранее заданное правило (центрирование при +0.3 п.п., CE при +1.0 п.п.), поэтому отчёт build отвечает на оба вопроса, а curve измеряет выбранную конфигурацию. Если CE не выбран, но прирост близок к порогу — r7-02 с принудительным CE или иной схемой.
