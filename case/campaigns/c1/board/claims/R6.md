# Claim R6 (ветка r6-multi, направление 6: ансамбль разных энкодеров из models.toml с центрированием)

Дата: 2026-11-05. Квота: 4 места (r6-01 ... r6-04). Родитель: r5-02 (центрирование bge-base, curve 0.77275; CV 0.8004). Не пересекаюсь с R4 (гибрид лексика+dense): моя линия - только dense-энкодеры, лексики нет.

## Гипотеза
Все прошлые dense-кандидаты (r2-*, r5-*) используют один backbone (bge-base). Энкодеры bge-base, bge-small, e5-small-v2, all-MiniLM-L6-v2 обучены на разных данных и ошибаются на разных запросах («ловушечные слова» у каждого свои), поэтому слияние их оценок поднимает acc@1 над лучшей одиночной моделью. Центрирование (вычитание среднего запросов и среднего каталога, r5-02: +2.4 п.п. по CV) применяется к каждой модели отдельно, т. к. у каждого пространства своё общее смещение (особенно e5/MiniLM с узкими косинусами).

## Механизм
- build (runner): для каждой из 4 моделей кодирует каталог и 556 обучающих запросов (sentence-transformers), проверяет numpy-энкодер против эталона; групповая 5-fold CV по family (те же фолды, что у r5) даёт оценки каждой модели для каждого запроса вне его фолда (mu_q по обучающей части фолда); перебираются слияния >= 2 моделей: z-score по навыкам внутри запроса с весами {0,1,2}^4 и RRF (k=10, 60) с весами {0,1}^4; выбирается лучшее по CV, при разнице <= 0.002 - с меньшим числом моделей. В /output - только модели с весом > 0.
- solve: numpy-энкодеры выбранных моделей (только с весом > 0), центрирование, косинусы, слияние (fusion.py - единственная реализация, общая с build).
- Одиночные модели и их CV записываются в report.json как справка.

## Область
Все стили; ожидаемо помогает casual/question/typo (разные токенизации и данные), на indirect выигрыш неясен (маленькие модели слабее по indirect, r2-03: bge-small 0.46 vs 0.56).

## Ожидаемый эффект
curve 0.77275 (r5-02) -> 0.79-0.82. CV (в report) fusion > bge-base centered (0.8004) на >= 1 п.п.

## Опровергающая проверка
- Лучшее слияние по CV < bge-base centered + 0.5 п.п., или curve <= 0.77275 + 0.01: разнообразие энкодеров не даёт выигрыша над сильнейшей моделью с центрированием.
- Если одиночные small-модели по CV слабее bge-base более чем на 8 п.п. и слияние не лучше: слабые модели лишь добавляют шум.
- Время: solve > 15 с на пример или build > 500 с - направление дорого.

## Происхождение train-сведений
`fit.jsonl` (556 записей train вне 50 семейств train_curve; та же выборка, что у r5-*). Назначение: средние векторы запросов (центрирование) и выбор слияния групповой CV (ADR-0004: обучение на train, калибровка). Таблиц запрос -> ответ и правил под запросы нет. Описано в README кандидата.

## Процедурное замечание
Локально поставлен только numpy (в ~/np_test, вне пакета) для синтетического теста логики build/solve на заглушках моделей со случайными векторами; реальные эмбеддинги/веса локально не считались.

## Дополнение (после r6-01: curve 0.79725, +2.45 п.п. к r5-02, парно 16/7)
r6-02 (родитель r6-01): режим слияния zlsm (z -> /tau -> log-softmax, сумма логарифмов, «произведение экспертов»), tau и веса выбирает та же групповая CV. Гипотеза: ошибки в верхушке ранжирования, z-сумма чувствительна к хвосту из 189 навыков. Ожидание: +0..1 п.п. к r6-01 (в пределах шума n=200). Опровержение: curve <= r6-01 + 0.005 и/или кривая по парным примерам без преимущества. Риск: CV выберет конфигурацию, эквивалентную z (тогда результат ~ r6-01).
