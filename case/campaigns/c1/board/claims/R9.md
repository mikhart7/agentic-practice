# Claim R9 (ветка r9-ltr, направление 9: рычаги против узкого места indirect — граф навыков (А) и GBDT-ранжировщик (Б))

Дата: 2026-11-05. Квота: 3 места (r9-01, r9-02, r9-03). База: r8-01 (ансамбль bge-base/e5-small/MiniLM 2/1/1 + центрирование + лексика w=0.1, train_curve 0.800).

## Анализ ошибок r8-01 на train_curve (чистый Python по `runs/r8-01-curve.json`)
47 промахов acc@1 из 200. Золотой навык на 2-м месте 21, на 3-м 6, вне топ-3 20 (indirect 15 из 20). Indirect: 30 верно / 4 на 2-м / 1 на 3-м / 15 вне топ-3. По кластеру каталога (`catalog_meta.jsonl`): у 24 из 47 ошибочный лидер из того же кластера, что золотой (cryptohopper-data vs crypto_prices_mcp, slack-explorer vs mcp-server-slack, google-cal-mcp vs sync-day/holiday-calendar). Остальные: «ловушечное слово» (invoices -> invoice-generator вместо памяти ассистента) и indirect без общих слов («spoken words of this talk from the big video site» -> bilibili вместо youtube-transcripts).
Вывод: ошибки двух типов — (1) 27 случаев золотой в топ-3, но не первый (соседи-близнецы, ловушки); (2) 20 случаев золотого нет в топ-3 (в основном indirect).

## Гипотезы и выбор
(А) Граф kNN навыков по эмбеддингам каталога (производная от описаний): Rocchio-PRF в пространстве оценок (q' = q + a*mean(топ-k навыков); эквивалентно оценке + a * средняя близость к топ-k), сглаживание оценки по k соседям, поправка на хабы (CSLS по статистике навыка на запросах train без меток). Механизм: у indirect нет общих слов, но кластер близких навыков находится по смыслу; усиление кластера подтягивает золотой, если в топ-k есть его сосед. Ожидаемо работает на типе (2); на типе (1) PRF усиливает лидера и вредит.
(Б) GBDT-ранжировщик (LightGBM lambdarank / бинарный) поверх навык-независимых признаков пары: z и ранги каждого энкодера, лексика, разрывы с лидером и вторым, оценки соседей навыка, близость к лидеру, число соседей в топ-3, доля навыка в массе кластера, PRF-признаки, длина и пики запроса. ID навыка не используется. Механизм: нелинейные правила («лидер и золотой — близнецы, лексика решает», «лидер уверенно оторван, ничего не менять»), недоступные линейным слияниям r4/r8 (`lr` не лучше `wz` в CV). Ожидаемо работает на типе (1).
Выбраны обе: (А) и (Б) вычисляются в одном build на одних фолдах, метод выбирается групповой CV; признаки графа входят и в (Б).

## Область, ожидаемый эффект
Все стили; цель — indirect и question/casual с близнецами. Ожидание скромное: CV +0.5..1.5 п.п. к wz (0.8383); curve 0.800 -> 0.805..0.815. r8 показал, что слияния упёрлись в шум; нового сигнала (кроме графа) нет.

## Минимальное изменение
r8-01 + `rank.py` (граф, PRF/сглаживание/CSLS, признаки пар, деревья LightGBM в JSON и их вычисление numpy в solve) + блок CV в build. Обучение только на `fit.jsonl` (556 записей train без семейств train_curve; ADR-0004), CV по семействам. LightGBM только в runner (build); в solve деревья считает numpy (без импорта lightgbm), согласие с LightGBM проверяет build (max diff < 1e-6).

## Опровергающая проверка
Групповая CV в build: если ни один новый метод не лучше `wz` (0.8383) более чем на 0.003, гипотезы (А)/(Б) опровергнуты на fit-выборке; curve не измеряется. Если лучший новый метод лучше `wz` в CV, но на curve не лучше r8-01 (0.800), перенос не подтверждён. Прирост PRF/графа должен быть на indirect (CV по стилям), иначе механизм «кластер подтягивает золотой» не подтверждён.

## Ограничения и среда
Локально: чистый Python для анализа ответов; numpy и lightgbm (в ~/np_test, вне пакета) только для проверки логики на случайных заглушках (чисел оттуда в выборах нет). Реальные эмбеддинги и оценки считает только runner (build). `diag.npz` в выходе build — диагностика оценок на fit-запросах (считается в runner, solve не читает), для анализа ошибок CV и проектирования следующей версии; в пакет не переносится.
