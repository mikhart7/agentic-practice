# Claim R5 (ветка r5-adapt, направление 5: обучение внутри build.py для улучшения dense-представления)

Дата: 2026-11-05. Квота: 4 места (r5-01 ... r5-04). Не пересекаюсь с R4 (гибрид лексика+dense): моя линия меняет только dense-представление запроса/навыка, лексики нет.

## Анализ ошибок (r2-04-curve, 60 ошибок acc@1 из 200; чистый Python по `runs/r2-04-curve.json`)
- 22 из 60 ошибок внутри кластера навыка, 38 в другом кластере; верного навыка нет в топ-3 у 28 из 60.
- По стилям ошибок: indirect 21/50, casual 10/30, question 10/32, cmd 7/50, typo 7/21, verbose 5/17.
- Класс ошибок: запрос с «ловушечным» словом, которое dense-представление принимает за тему (`invoices` -> навыки про счета вместо `frugal-memory`; `photos` -> `gemini-image-studio` вместо поиска картинок; `ticket/repo` -> `github-issue-mcp` вместо `codehost-port`). Это не лексическая, а доменная ошибка метрики сходства: общий bge не знает, что «из запроса важно» для описаний этого каталога (короткое «what it does» против 6 стилей запросов).

## Гипотеза
Небольшое обучаемое отображение поверх замороженного bge-base (общее для всех навыков, обучается контрастивно по парам запрос -> верный навык, CE по каталогу, L2-регуляризация к тождеству) калибрует пространство под распределение «запрос пользователя - краткое описание навыка» и повышает acc@1 на других навыках (перенос по семействам). Дополнительно: центрирование (вычитание среднего эмбеддинга запросов/навыков) убирает общую компоненту, раздувающую косинусы.

## Механизм
- `build.py` (в runner): кодирует каталог и обучающие запросы (556 записей train вне семейств train_curve, файл `fit.jsonl` в пакете; у каждого навыка в train одно семейство из 4 перефраз => группа семейств = отложенный навык) bge-base; набор конфигураций (центрирование, режим: query-adapter / shared-adapter / ridge, λ, число шагов) оценивается 5-fold групповой CV по семействам (метрика кейса); выбирается лучшая по CV; если не лучше базы на порог -> тождество; финальная подгонка на всех 556; `report.json` с таблицей CV по конфигурациям, по стилям, гиперпараметрами; плюс замер времени шага дообучения энкодера в runner (разведка для (в), на качество не влияет).
- `solve.py`: как r2-04 (numpy-энкодер, ансамбль запроса plain+инструкция), затем центрирование и матрица A к вектору запроса; эмбеддинги навыков уже преобразованы в build.
- Идея (г) (усреднение эмбеддинга навыка с эмбеддингами его обучающих запросов) на нашем разбиении не проверяема: у каждого навыка в train ровно одно семейство, семейство train_curve исключено целиком, поэтому для навыков curve обучающих запросов нет, а на остальных нет отложенного «другого намерения». Не выбираю; риск заучивания экземпляров.

## Область
Все запросы; ожидаемо помогают casual/question/cmd и «смежный кластер», indirect меньше.

## Ожидаемый эффект
train_curve 0.7425 (r2-04) -> 0.75-0.78; если CV в build не показывает прироста над базой, адаптер выключится (тождество), результат совпадёт с r2-04 (отрицательный результат).

## Опровергающая проверка
- CV по группам в build не превосходит базу более чем на 0.5 п.п. => линейный адаптер на 556 запросов не даёт переноса.
- train_curve не выше r2-04 (0.7425) более чем на шум (SE ~3 п.п.) при CV-приросте => CV не переносится на curve.

## Происхождение train-сведений
`fit.jsonl`: 556 записей из `case/dataset/train.jsonl` (id, запрос, верный навык, family, style) за вычетом всех семейств train_curve (50). Назначение: обучение общего линейного отображения (768x768) и подбор нескольких гиперпараметров CV в build; пункт ADR-0004 «обучение на train: линейный адаптер запроса, калибровка». `solve.py` файл не читает. Таблиц «запрос -> ответ» и правил под запросы нет.
