# Как устроена арена


Используем [арену DeepPavlov](https://gitlab.deeppavlov.ai/deeppavlov/arena) без изменений, коммит `a28eee3` ([ADR-0001](adr/0001-methodology.md)). Своей методологии нет, поэтому таблицы отличий тоже нет.

## Роли и зачем каждая
- **Оператор (я).**
  - Раскладываю данные и запускаю оценщиков.
  - Только я вижу результат private.
  - Это доверенный контур: кто-то должен держать закрытые данные.
- **Агент подготовки** — отдельный запуск Claude Code с `prompts/prepare.md` в контейнере исследователя.
  - Проверяет постановку, замораживает пакет метрики, настраивает train-сервис с build, фиксирует `campaign.md` и пишет `preparation.md` со свидетельствами.
  - Отдельный, потому что правила кампании должны быть зафиксированы до поиска. Иначе поиск мог бы менять метрику или условия под свои результаты.
- **Оркестратор** — запуск Claude Code с `prompts/start.md` в контейнере исследователя.
  - Ведёт карту направлений и счётчик лимита, раздаёт задачи, выбирает финалистов.
- **Исследователи** — субагенты оркестратора, у каждого свой git worktree.
  - Цикл: гипотеза → изменение → регистрация → замер → выводы.
  - Отдельные worktree, чтобы параллельные направления не мешали друг другу.
- **Ревьюер** — субагент. До private проверяет каждого финалиста:
  - нет заученных запросов и утечек;
  - векторы и веса получены в build (есть квитанция), а не положены готовыми;
  - соблюдены разрешённые изменения.

  Ревьюер — агент, а не программа, потому что «подгонку» и обход правил нельзя полностью описать заранее. Оценщик, наоборот, — программа: он должен быть детерминированным и без суждений.
- **Оценщики** (train, public, private) — сервисы арены.
  - Каждый хранит свои данные и метрику.
  - Запускает кандидата и отдаёт наружу только разрешённое.
  - Train-сервис ещё выполняет build: один раз запускает `build.py` кандидата и публикует результат (векторы каталога, обученные веса).
- **Runner** — одноразовый контейнер на каждый запрос, а в режиме build — один запуск `build.py` на кандидата. Модели и torch есть только здесь, в контейнере исследователя их нет.
  - Кандидат — чужой код, поэтому он заперт: нет сети, 2 CPU, 2 ГБ, файловая система только для чтения.

Оркестратор, исследователи и ревьюер — один запуск Claude Code с одинаковыми правами. Изоляция проходит не между ними, а между ними и закрытыми данными.

## Видимость train / public / private и от чего она защищает
| Раздел | Размер | Что видит исследователь | От чего защищает |
|---|---|---|---|
| train | 756 запросов | всё: запросы, эталоны, ответы по каждому примеру | — (на нём учатся) |
| public | 380 | только общий score кандидата, один раз на кандидата | от подгонки под конкретные примеры: по одному числу этого не сделать |
| private | 376 | ничего, только статус | от любой подгонки: финальная цифра на данных без обратной связи |

- Деление идёт целыми **семействами** (намерение + 4 перефразы). Иначе перефраз из train «узнавался» бы в private, и мы мерили бы заучивание, а не обобщение.
- Private проверяется **один раз** и только для финалистов. С пятью попытками он стал бы вторым public: можно было бы выбирать вариант по private-результату, и итоговая цифра была бы смещена вверх.

## Лимит предложенных решений и почему не токены
- Лимит — **60 предложенных решений** ([ADR-0005](adr/0005-campaign-limit.md)).
- Считается каждое зарегистрированное решение, включая сломанные. Иначе можно было бы бесплатно пробовать всё подряд и выдавать за неудачу только плохое. Неудача — тоже информация, и она остаётся в журнале.
- Токены и время измеряются, но не ограничивают: от них зависят модель и харнес, а число решений одинаково понятно для любой задачи.
- Лимит заставляет выбирать, что пробовать, и задаёт ось X кривой.

## Журнал: родословная, снимки, кривая, AUC
- **Журнал** (`search.sqlite3`) хранит по каждому кандидату:
  - id и родителей (их может быть несколько);
  - гипотезу;
  - неизменяемый снимок файлов;
  - все замеры с условиями.

  Исправил одну строку — значит, это новый кандидат.
- **Родословная** — дерево «кто от кого». Показывает, какие ветки дали рост, а какие оказались тупиками.
- **Кривая** — лучший score на `train_curve` (200 запросов) в зависимости от числа предложенных решений к моменту окончания замера.
  - Она не убывает: в каждой точке берётся лучший результат на данный момент, а неудачный кандидат его не уменьшает.
- **AUC** — площадь под ступенчатой кривой до горизонта 60; `mean_quality = AUC / 60`.
  - Два поиска, пришедшие к 0.75, различаются AUC: у кого он больше, тот нашёл хорошее раньше, то есть потратил меньше решений.
  - Замер привязан к числу предложений на момент окончания. Поэтому если зарегистрировать много кандидатов до первых результатов, рост сдвигается вправо и AUC падает. AUC указываем вместе с конечным качеством.
- Шум на 200 запросах — около 3.5 п.п. Скачок меньше ~5 п.п. может быть случайностью.

## Финализация: K финалистов → private → N лучших
1. Поиск заканчивается, когда исчерпан лимит или дана явная команда остановиться.
2. Оркестратор выбирает ровно **K = 5** финалистов. Критерии:
   - качество на `train_curve` и public;
   - разрыв train↔public как признак переобучения;
   - разнообразие подходов (не пять вариаций одного);
   - ревью без замечаний.
3. `evaluator.search finalize` фиксирует набор, после этого новых кандидатов не будет.
4. Набор одним пакетом и один раз уходит в private. Оценщик выбирает **N = 2** лучших.
   - Два, а не один: при шуме ~2.5 п.п. первые места легко путаются.
   - Второе решение может быть почти таким же по качеству, но дешевле по времени: правило равенства арены — при равном качестве выигрывает более быстрое.
5. Результат вижу только я. Ключевая цифра — выращенное решение против BM25 на private.

## Граница изоляции в моей установке
Правило арены: изоляция держится на правах доступа, а не на промпте. «Не смотри в private» — просьба, а агент с доступом к файлу может прочитать его случайно (поиск по диску, `grep -r`) или обойти просьбу. Поэтому нужно, чтобы читать было физически нечего.

- **Закрытые данные** лежат в `/srv/arena/{public,private,secrets,state}`, режим 0700, владелец UID 10001. Исходники у оператора — `~/arena-private`.
- **Исследователь** — контейнер `researcher` (штатный из `compose.yaml`). Он видит:
  - `/workspace` — клон репозитория с train;
  - `/search` — журнал;
  - свои submit-токены.

  У него нет:
  - Docker socket и sudo;
  - `/srv/arena`;
  - домашнего каталога оператора с `~/arena-private` и транскриптами `~/.claude`;
  - доступа к Windows через WSL.

  Именно через эти пути агент под моей учёткой увидел бы private.
- **Оценщики public и private** — два экземпляра `evaluator`, наружу отдают число или статус.
- **Кандидаты** — runner без сети.
- **Что схема не защищает:**
  - от меня как администратора;
  - от подготовительной сессии Claude, которая генерировала данные: она видела private, поэтому подготовка арены и поиск — другие сессии, в контейнере;
  - от утечки через git — это закрывает проверка n-грамм перед каждым push.
- **Наши дополнения к штатной схеме** ([ADR-0006](adr/0006-isolation.md)):
  - Claude Code в образе — арена говорит, что харнес добавляет оператор;
  - постоянный `HOME` исследователя для логина и трейсов;
  - адреса оценщиков через `host.docker.internal`;
  - подготовка арены тоже в контейнере исследователя, а не на хосте;
  - train-сервис с build — конфигурация нашего кейса по образцу `sc35`.
