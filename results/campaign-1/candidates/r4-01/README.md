# r4-01: гибрид лексики (r1-03) и dense (bge-base, r2-04) с параметрами слияния, обученными в build на train

Родители: r1-03 (лексика, train_curve 0.6415), r2-04 (dense bge-base, ансамбль запроса plain + инструкция BGE, 0.7425), r2-02 (dense, 0.7395).

## Гипотеза
Ошибки dense (R2): путаница близких навыков кластера и короткие запросы; у части запросов есть сильные лексические подсказки (имена сервисов, точные слова). У лексики (R1) провал на indirect (нет общих токенов). Два источника ошибаются по-разному, поэтому слияние должно дать больше, чем любой из них (ожидание: 0.76-0.80 на train_curve). Опровержение: score не выше r2-04 (0.7425) более чем на ~1 п.п.

## Механизм
- solve считает для запроса: dense-косинусы (два вида запроса: без префикса и с инструкцией BGE) к `emb.npy` из `/assets/prepared`, сырой BM25 и косинус триграмм слов (код r1-03, `lex.py`); из них признаки (`fuse.py`): z-оценки по навыкам, ранги, разности, длина запроса.
- Слияние задаёт `/assets/prepared/fusion.json` (метод + параметры), который пишет только build. Методы-кандидаты: `wz` (z(dense) + w * z(лексика r1-03)), `wz2` (z(dense) + wb*z(BM25) + wt*z(триграммы)), `rrf` (1/(k+rank_dense) + w/(k+rank_lex)), `lr` (листовая softmax-регрессия на 9 признаках: z двух видов dense, z BM25, z триграмм, BM25/max, косинус триграмм, отставание dense от максимума, взаимодействие с длиной запроса).
- build выбирает метод и параметры групповой кросс-валидацией (5 долей по `family`, вложенно: параметры подбираются на 4 долях, оцениваются на пятой) и обучает выбранный метод на всех обучающих записях. Отчёт — `report.json` (поле `fusion`: dense_only / lex_only / cv по методам / выбранный метод и параметры).

## Происхождение train-сведений (ADR-0004)
- Файл `train_fit.jsonl` (556 записей) — выборка из `case/dataset/train.jsonl` + `train.meta.jsonl` (id, input, family, style, список релевантных id). Скопирован скриптом без изменения текстов; sha256 файла `2a6d1d82...c3d4b5` (проверяется равенством с отфильтрованным train).
- Назначение: **только обучение общего механизма слияния в build.py** (несколько скаляров/9 весов), пункт ADR-0004 «обучение на train в build». solve `train_fit.jsonl` не читает; в `/assets/prepared` пишутся только `emb.npy` (эмбеддинги каталога, посчитанные в build), `ids.json`, `config.json`, `fusion.json` (метод и числа), `report.json`. Таблицы «запрос -> ответ» и правил под конкретные запросы нет.
- Честность замера train_curve: из обучающих записей исключены все 50 семейств, входящие в `train_curve` (200 запросов); остались 556 записей, 139 семейств. Семейства совпадают с навыками один к одному, пересечения навыков train_curve и обучающих записей нет (проверено: 0 общих primary). Кросс-валидация по family.
- Для public-кандидата можно включить все 756 записей (тогда train_curve перестанет быть независимым замером); в этой версии не делается.
- В пакет не положены ответы, индексы или эмбеддинги, посчитанные вне build. Dense-признаки обучающих запросов считаются в build той же моделью, что эмбеддинги каталога.
