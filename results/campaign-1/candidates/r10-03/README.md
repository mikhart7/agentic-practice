# r10-03: r4-01 (лексика r1-03 + dense bge-base, обученное слияние), build обучается на всех 756 записях train

Родитель: r4-01 (train_curve 0.7825 при обучении на 556 записях без семейств curve). Ветка `r10-refit`, claim `board/claims/R10.md`, findings `board/findings/r10.md`.

## Гипотеза
Параметры слияния лексики и dense (несколько скаляров или 9 весов `lr`) навык-независимы; больше данных (756 вместо 556, +36%) и охват всех 189 навыков/семейств (вместо 139) снижают дисперсию их оценки и могут улучшить перенос. Опровергает: score public не выше r4-01.

## Что изменено относительно r4-01
Только данные обучения и гигиена. `build.py` читает `train.jsonl` + `train.meta.jsonl` (копии `case/dataset/*` без изменений; склейка по id — `trainset.py`) вместо `train_fit.jsonl` (556 записей); поле релевантных навыков называется `relevant` вместо `gold`. Признаки (`fuse.py`), подбор (`fit.py`), лексика (`lex.py`), `solve.py`, `enc.py`, `params.json` не менялись. `train_fit.jsonl` удалён. В пакете нет `__pycache__`/`*.pyc`.

## Механизм (как у r4-01)
- solve считает для запроса: dense-косинусы (два вида запроса: без префикса и с инструкцией BGE) к `emb.npy` из `/assets/prepared`, сырой BM25 и косинус триграмм слов (`lex.py`); из них признаки (`fuse.py`): z-оценки по навыкам, ранги, разности, длина запроса.
- Слияние задаёт `/assets/prepared/fusion.json` (метод + параметры), его пишет только build. Методы-кандидаты: `wz` (z(dense) + w * z(лексика)), `wz2` (z(dense) + wb*z(BM25) + wt*z(триграммы)), `rrf`, `lr` (softmax-регрессия на 9 признаках).
- build выбирает метод и параметры групповой 5-fold CV по `family` (вложенно: параметры подбираются на 4 долях, оцениваются на пятой) и обучает выбранный метод на всех обучающих записях. **Итоговый метод и параметры выбирает сам build по этим данным**; они записаны в `fusion.json` и `report.json` (поле `fusion`: dense_only / lex_only / cv по методам / выбранный метод, параметры). Здесь значения не фиксируются, чтобы не устареть; для справки r4-01 на 556 записях выбрал `lr`.
- Зависящие от времени ветки: явных бюджетов времени в build нет; таймаут build 600 с (r4-01: ~120 с на 556 записях). **Запасной вариант:** если обучение слияния падает (исключение), build записывает `fusion = wz, w = 0.5` и причину в `report.json` (`fit_error`); поэтому перед использованием проверяй отсутствие `fit_error`.
- Dense-признаки обучающих запросов считаются в build той же моделью, что эмбеддинги каталога (sentence-transformers), `solve` использует numpy-энкодер (`enc.py`), проверенный в build против эталона (`numpy_encoder_ok`).

## Происхождение train-сведений (ADR-0004: «обучение на train в build»)
- `train.jsonl` (756 запросов, sha256 `9c2e9857f611e37398d7e4dcb3d7066753850798f9356fa3148acb702b6e767a`) и `train.meta.jsonl` (sha256 `0cbb754b13d668af63e8350465e1f7fd55c9a870ba3da3610b14fe571b3e970c`) — точные копии `case/dataset/train.jsonl` и `train.meta.jsonl`. Контрольные суммы пишутся в `report.json` (`train_sha256`).
- Назначение: **только обучение общего механизма слияния в build.py** (несколько скаляров/9 весов). solve эти файлы не читает; в `/assets/prepared` пишутся `emb.npy` (эмбеддинги каталога, посчитанные в build), `ids.json`, `config.json`, `fusion.json` (метод и числа), `report.json`. Таблиц «запрос -> ответ» и правил под конкретные запросы нет.
- **`train_curve` при таком обучении не является независимой проверкой**: все 200 его запросов и 50 семейств входят в обучающие 756 записей (в r4-01 они исключались). Score на `train_curve` этой версии не оценивает перенос на новые навыки; эффект уточнения проверяется только на public оркестратором.
