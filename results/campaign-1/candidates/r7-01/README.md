# r7-01: гибрид r4-01 + центрирование dense + кросс-энкодер как признак; выбор конфигурации по CV в build

Родители: r4-01 (лексика r1-03 + bge-base, обученное слияние, train_curve 0.7825), r5-02 (центрирование dense, 0.77275, CV +2.4 п.п. над dense), r3-02 (кросс-энкодер MiniLM над лексикой, +0.03).

## Гипотезы
1. Центрирование dense-косинусов (вычитание среднего запросов и среднего каталога) убирает общее смещение пространства bge («хабы» среди навыков) и даёт эффект сверх слияния r4-01. Z-оценка по навыкам внутри запроса снимает сдвиг запроса, но не смещение навыков, поэтому эффект не обязан поглощаться слиянием.
2. Кросс-энкодер ms-marco-MiniLM-L6-v2 как признак на кандидатах гибрида (топ-8 dense + топ-8 лексики): у r4-01 из 49 промахов acc@1 22 имеют верный навык на 2-3 месте (в топ-3 nP@3 0.85 при acc@1 0.75). Кросс-энкодер видит запрос и описание вместе. Потолок прироста по R3 около +0.03; чтобы окупаться, нужно заметно больше. В solve кросс-энкодер идёт через numpy (как bi-encoder, без torch), поэтому цена по времени порядка секунды, а не 9-10 с.

## Механизм
build.py (runner) считает эмбеддинги каталога и 556 обучающих запросов (два вида запроса, как r4-01), признаки лексики r1-03 и сравнивает по групповой 5-fold CV по family (те же фолды, что у r4-01/r5) варианты: raw (r4-01), cen (центрированные dense-косинусы), raw+ce, cen+ce (логиты кросс-энкодера на кандидатах как два признака: z внутри кандидатов и отставание от лучшего, softmax-регрессия `lrce` только на кандидатах). Методы слияния: `wz` и `lr` (как в r4-01). Правило выбора (`fit.choose`, задано до измерения): центрирование включается, если CV лучше не меньше чем на 0.003; кросс-энкодер — если лучше не меньше чем на 0.01. Выбранный вариант обучается на всех 556 записях. `report.json`: CV по вариантам и стилям, парные сравнения (запросов лучше/хуже), время, проверка эквивалентности numpy-кросс-энкодера эталону (порог 2e-3 по логиту).
solve.py читает `fusion.json` и применяет выбранное: центрирование (emb.npy уже центрирован, mu_q.npy), лексика, при `ce.enabled` — кросс-энкодер (numpy, при непрохождении проверки transformers).

## Происхождение train-сведений (ADR-0004)
`train_fit.jsonl` — 556 записей train (id, input, family, style, gold) из `case/dataset/train.jsonl` + `train.meta.jsonl`, без 50 семейств `train_curve` (тот же файл, что у r4-01, sha256 `2a6d1d82...c3d4b5`). Назначение: только обучение общих параметров в build: средние запросов (2x768 чисел), веса слияния (11 коэффициентов), выбор конфигурации по CV. solve файл не читает. Таблиц «запрос -> ответ» и правил под запросы нет, эмбеддинги и веса вне build не считались. Средние запросов считаются по всем 556 запросам (безметочная статистика, в CV по фолдам не пересчитывается — разница пренебрежима и не затрагивает метки).

## Файлы
`build.py`, `solve.py`, `fit.py`, `fuse.py`, `lex.py` (r1-03), `enc.py` (numpy BERT bi-encoder из r2-02 + `CrossEncoderNP`), `params.json`, `train_fit.jsonl`.
